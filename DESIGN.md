# coopTracker — дизайн

Статус: обновлён 2026-11-05, идёт шаг 1 (`graph-core`). **Открыто** — не решено, нужно решить до соответствующего шага.

Решения здесь часто принимаются по ходу разработки и могут меняться. Поэтому режимы и правила делаем настройками-данными, а не развилками в коде. Решения, которые дорого отменить (схема БД, протокол, авторизация), обсуждаем до принятия.

## Что это

Трекер задач и роадмап, где основной вид — нодовый граф из блоков с задачами (стиль — см. «Визуальный стиль»). Стрелка «A блокирует B» делает статусы вычисляемыми: закрыл задачи — следующие блоки разблокировались. Работает соло и в коопе в реальном времени. Сначала для себя и друга, потом, возможно, для организаций.

## Термины

- **Envi** (environment) — пространство: основная роадмапа, её ветки, участники и настройки. Аналог репозитория на GitHub.
- **Организация** — контейнер для envi. Каждый envi принадлежит ровно одной организации; у каждого пользователя есть личная.
- **Нода** — то, что стоит на холсте. Три вида: **блок** (карточка с шапкой, описанием и списком задач), **роадмапа** (вместо задач открывается во вложенный граф) и **milestone** (точка вроде «Релиз 1.0»).
- **Задача** — пункт внутри блока: статус, ответственные, срок и остальные поля.
- **Уровень** — корневой граф envi или вложенный граф внутри роадмапы. Глубина вложенности максимум 1.
- **Стрелка (ребро)** «блокирует»: A → B означает «B нельзя начать, пока A не выполнен». Идёт от выхода ноды («нода выполнена целиком») или от выхода задачи («выполнена эта задача») ко входу другой ноды. Может пересекать границу вложенной роадмапы в любом направлении.
- **Ветка** — отдельная версия графа envi. Есть `main` и пользовательские ветки; офлайн-правки живут в локальной ветке.
- **Операция (op)** — атомарное изменение графа. Все изменения — только операциями.
- **PR** — предложение перенести изменения одной ветки в другую, с preview и апрувом.

## Роли

- **master** — владелец envi. Их может быть несколько; создатель envi становится master. Только master меняет настройки envi.
- **member** — участник.
- **viewer** — только просмотр: видит всё, ничего не меняет (заказчик, менеджер, другая команда).

Создатель envi — **creator**: master с пометкой `[creator]` справа от имени. Он один на envi.
- Другие master не могут снять с него роль master.
- Он может передать статус creator другому master.
- Удалить envi может только creator.

Владелец организации автоматически master во всех её envi (как владельцы организации на GitHub).

Менять любую задачу (поля, статус) может любой member; viewer не меняет ничего. Всё видно в истории изменений.

## Принятые решения

| Решение | Почему | Отвергнуто |
|---|---|---|
| Сервер-авторитет, не CRDT | Данные — записи, а не текст; «побеждает последний» на уровне поля достаточно. Инварианты графа (нет циклов, нет висячих рёбер) проверяются в одной точке. Конфликты веток показываются человеку, а не сливаются молча. Так же устроены Figma и Linear. | Yjs: инварианты только чинятся после слияния, данные — непрозрачный blob, плохо для запросов и прав организаций. |
| Свой сервер: Node + TypeScript, Fastify, WebSocket | Цель — разобраться в бэкенде самому, полный контроль над протоколом. | Convex, Supabase: меньше кода, но синхронизацию за вас делает платформа. |
| PostgreSQL в Docker (`docker compose`) | Стандарт, подходит для организаций без переезда. Docker Desktop уже установлен; локально то же, что будет на сервере. | SQLite; установщик Postgres под Windows. |
| Drizzle для работы с БД | Все значения параметризуются автоматически (защита от SQL-инъекций). Схема на TypeScript, миграции генерируются сами — не нужно писать SQL изменения таблиц руками. | Чистый `pg` (одна склейка строк — и дыра), Kysely (миграции руками), Prisma. |
| React + Vite (SPA) | Приложение за логином, SSR и SEO не нужны. React Flow — родная библиотека. | Next.js. |
| React Flow (`@xyflow/react`) | Стандарт для нодовых редакторов с портами. | tldraw (свободный холст), Rete.js (меньше экосистема). |
| dagre за функцией `layout()` | Простой и достаточный для DAG. Вложенные уровни раскладываются отдельно, поэтому ELK пока не нужен. | ELK — если понадобится. |
| Общий пакет `graph-core` | Одна и та же логика (валидация, статусы, слияние) на клиенте и сервере. Тестируется без браузера и сети. | Логика внутри React-компонентов. |
| Монорепо на npm workspaces: `graph-core`, `server`, `web` | npm уже установлен, отдельный инструмент не нужен. | pnpm, turborepo — пока лишнее. |
| Vitest + fast-check | Юнит-тесты и property-based тесты на случайных графах. | — |
| Приватный репозиторий на GitHub | Доступ для друга, история, позже CI. Репозиторий и доступы пользователь создаёт сам; Claude не указывается соавтором в коммитах. | Только локальный git. |
| ID генерирует клиент (UUID v7) | Ноды можно создавать офлайн без сервера; повторная отправка операции идемпотентна. | ID от сервера. |

## Настройки envi

Задаются при создании, потом их может менять только master. При создании у каждого варианта короткое пояснение; по умолчанию стоят самые свободные.

- `mainProtected` — структуру `main` (ноды, рёбра, удаления) можно менять только через PR из веток. Если выключено, все правят `main` вживую.
- `statusMode` — как задача становится выполненной. Это отдельная ось от `mainProtected`: статусы всегда меняются прямо в `main`, не через PR.
  - `free` (по умолчанию) — участник сразу ставит `done`.
  - `review` — участник ставит «выполнено», задача переходит в `in_review` и все в `main` это видят. master подтверждает (→ `done`) или отклоняет (→ `in_progress`). master может ставить `done` сразу.
- `reviewUnlocks` (только при `review`) — разблокирует ли задача `in_review` следующие задачи до подтверждения. Если да и master отклонил, следующие задачи снова блокируются.
- `offlineMerge` — что делать с офлайн-правками при подключении: `auto` (применить сами, если нет конфликтов; при конфликте показать preview автору) или `always-pr`.
- `approval` — кто апрувит PR: `masters` (автор-master может апрувить свой PR, только если включено `allowSelfApprove`) или `any-other-member` (любой участник, кроме автора).
- `estimateUnit` — в чём оценка задач: `hours` (часы) или `points` (условные очки).
- `visibility` — кто видит envi: `private` (по умолчанию — только приглашённые и владельцы организации) или `org` (все участники организации, как минимум viewer). Как private и internal репозитории на GitHub.
- `taskPrefix` — префикс номеров задач (например, `CT` → CT-42). Задаётся при создании; если master его меняет, номера задач сохраняются.

Режим strict (отметка скрыта до апрува) рассматривали и убрали: он проигрывает `review` во всём — контроль тот же, но никто не видит, что работа сделана.

## Холст

- Фон — сетка (в React Flow это встроенный `Background`: точки, линии или крестики).
- master может выбрать цвет фона envi. Сетка остаётся поверх фона.
- Сетку каждый отключает у себя локально (настройка хранится в браузере, на других не влияет).
- Блоки привязываются к сетке по умолчанию; с зажатым Alt ставятся свободно. Координаты всегда целые. Привязка работает и при выключенной у себя сетке.
- Масштаб и прокрутка холста у каждого свои и хранятся в браузере, в граф не попадают.
- Картинок как фона нет совсем: им нужно хранилище файлов, а задачу «показать на холсте, что к чему» решает слой рисования.

**После MVP (предложено), Открыто:**
- **Слой рисования в стиле Excalidraw** поверх фона и под нодами: рисованные от руки линии, стрелки, прямоугольники, текст — чтобы указывать на блоки и подписывать области. Элементы — векторные данные (операции `createDrawing` / `updateDrawing` / `deleteDrawing`), файлы не нужны; двигаются и масштабируются вместе с холстом. Два пути реализации, решим при подходе:
  - встроить саму библиотеку Excalidraw (MIT) вторым слоем — много готового, но два холста придётся синхронизировать по масштабу и решать, какой слой ловит мышь; к тому же у Excalidraw своя модель совместной работы, которую надо стыковать с нашей;
  - свой простой слой на roughjs (именно он даёт Excalidraw «рисованный» вид) — меньше возможностей, но всё в нашей модели операций.

  Открыто: кто может рисовать; идут ли рисунки через PR при защищённом `main` (предложено: нет, это пометки, а не структура).
- **Комментарии к блокам**: обсуждение у ноды (автор, время, «решено»). Хранятся отдельно от графа веток и не идут через PR. Открыто: нужны ли упоминания и уведомления.

## Язык интерфейса

Русский и английский, с основой под любые другие языки: все тексты интерфейса — в файлах переводов, а не в коде. Нужна поддержка русских множественных форм (1 задача, 2 задачи, 5 задач), поэтому библиотеку переводов берём с форматом ICU (выберем на шаге `web`). `graph-core` и сервер возвращают коды ошибок, а не текст: текст подставляет интерфейс на языке пользователя. Письма тоже на двух языках.

## Визуальный стиль

Референс — [docs/references/node-editor.png](docs/references/node-editor.png). Берём стиль, а не игровые элементы интерфейса:
- Серая тема по умолчанию (не чёрная), компактная мелкая типографика. Все цвета — через CSS-переменные (дизайн-токены), чтобы в самом конце можно было добавить ~6 палитр без переписывания. Цвета статусов должны различаться в любой палитре.
- Холст с сеткой, миникарта в углу, индикатор масштаба и кнопка «вписать всё».
- Нода: цветная шапка с иконкой и названием, тело с полями, вход слева, выход справа. Выделенная нода — цветная рамка.
- Рёбра — плавные светлые кривые.
- Нода-блок как карточка на референсе: цветная шапка с названием, описание, список задач; у каждой задачи свой выход справа, у шапки — выход «блок выполнен целиком», вход слева.
- Правая панель — инспектор выбранного блока или задачи со сворачиваемыми секциями (название, статус, ответственные, описание, предупреждения).
- Верхняя панель — действия envi (ветка, PR, настройки, экспорт).

- Левая панель (решение по умолчанию, поменяем, если не зайдёт) — вкладки:
  - «Структура» — дерево: корневой граф и вложенные роадмапы, переход по клику;
  - «Ветки и PR»;
  - «Входящие» — задачи на проверке (для master) и предупреждения.

  Лента активности — позже; данные для неё уже есть в логе операций.
- Нижней панели нет: весь низ отдан холсту.

## Производительность и удобство холста

**Чтобы не лагало** (по документации React Flow и опыту tldraw):
- Главная причина тормозов — лишние перерисовки. Компоненты нод мемоизированы, каждый подписан только на свои данные и не читает весь список нод. `graph-core` не пересоздаёт неизменённые объекты.
- Лёгкий CSS на нодах: без теней, градиентов и анимаций. Статичный пунктир дешёвый, «бегущий» анимированный — нет.
- **Упрощённый вид при отдалении**: на мелком масштабе блок показывает только шапку и полоску прогресса.
- Длинный список задач в блоке показывает первые ~8 и «ещё N»; блок можно свернуть до шапки (у себя, локально).
- Отрисовку только видимого (`onlyRenderVisibleElements`) включаем, только если замеры на наших графах покажут выигрыш — отзывы о ней противоречивые.
- Тяжёлое (автораскладка) — в Web Worker, чтобы не подвисал интерфейс.
- Курсоры других участников приходят не чаще ~20 раз в секунду, а браузер плавно достраивает путь между точками (кандидат — библиотека perfect-cursors, обсудим на шаге 5).

**Удобство в MVP:**
- Проверка стрелки во время перетаскивания: краснеет, если создаст цикл или тупик (та же проверка из `graph-core`).
- Привязка к сетке и **направляющие** выравнивания с соседними блоками при перетаскивании.
- **Режим фокуса**: выделил задачу или блок — подсвечивается вся цепочка (что блокирует и что блокируется им), остальное приглушается.
- **Командная палитра Ctrl+K**: поиск задач по номеру и названию с переходом на холсте, действия с клавиатуры.
- **Фильтры** по меткам, ответственным, статусу: неподходящее приглушается, а не исчезает, чтобы стрелки не висели в воздухе.
- Отклонённая сервером правка откатывается, и показывается уведомление на языке пользователя.
- Статус показывается цветом **и** иконкой (не только цветом); учитываем системную настройку «уменьшить движение».

## Модель данных графа

Точные типы — в [types.ts](packages/graph-core/src/types.ts) и [ids.ts](packages/graph-core/src/ids.ts); здесь — смысл и правила.

- **Ноды** стоят на холсте и бывают трёх видов:
  - **блок** (`BlockNode`) — карточка с шапкой, описанием и списком задач;
  - **роадмапа** (`RoadmapNode`) — вместо списка задач открывается во вложенный граф из нод;
  - **milestone** (`MilestoneNode`) — точка вроде «Релиз 1.0», без задач.

  Общие поля: `id`, `parentId` (`null` — корневой уровень, иначе id роадмапы), `title`, `description`, `x`, `y`, пометка «засчитано» (`countedDone`, см. «Когда выполненное снова не выполнено»), авторство и время. У блока и роадмапы ещё срок и метки, у milestone — срок.
- **Задачи** лежат только внутри блоков (`blockId`), в порядке `order`. Поля задачи: номер, название, описание, статус, ответственные, срок, приоритет, метки, оценка, предупреждения, авторство.
- **Стрелка (ребро)** — `id`, `source`, `target`. Источник — выход в шапке ноды (`{ kind: 'node' }`, «нода выполнена целиком») или выход у задачи (`{ kind: 'task' }`, «выполнена эта задача»). Цель хранится в той же форме (`{ kind: 'node' }`): сейчас вход есть только у нод, а вход у отдельной задачи можно добавить позже без переделки сохранённых данных. Разные зависимости внутри одного блока решаются делением на блоки; взять задачу раньше можно через «Досрочно». Стрелка может соединять разные уровни (см. «Стрелки через границу роадмапы»).
- **Граф ветки** — `{ nodes, tasks, edges }`, обычные объекты по id, а не `Map`: снимок напрямую сериализуется в JSON (WebSocket, экспорт, IndexedDB).
- **id брендированные**: во время работы это обычные строки, но компилятор не даёт перепутать, например, id задачи с id пользователя. Строка превращается в id (`asNodeId`, `asTaskId` и т. д.) только там, где id появляются: создание, чтение из БД, разбор входящих сообщений, тесты.
- Пустое значение — `null`, а не отсутствующее поле. В изменении (`NodePatch`, `TaskPatch`) пропущенное поле значит «не трогать», `null` — «очистить».
- **Позиции нод** — целые пиксели в координатах холста: точное сравнение «двигали или нет» при слиянии, никакого шума вроде `120.00000000000001`, колонка `integer` в БД. Масштаб и прокрутка холста в граф не входят.
- **Неизменённое не пересоздаётся**: после операции ноды, задачи и стрелки, которых она не коснулась, остаются теми же объектами. Тогда интерфейс перерисовывает только изменившееся.
- **Порядок задач** — дробный индекс: строка «между» соседями, как в Figma. Вставка между двумя задачами не сдвигает остальные, поэтому одновременные перестановки не конфликтуют. Если двое получили одинаковый индекс, порядок решает id.
- **Лимиты** (`LIMITS`): до 10 ответственных, до 20 меток (без повторов), название до 200 символов, описание до 20 000, дробный индекс порядка — непустой, до 128 символов. Пустое название допустимо: блок или задачу создают, а название вводят следом. Оценка — неотрицательное конечное число, дробное допустимо.
- **Формат срока**: дата — `YYYY-MM-DD`, и такая дата существует; дата со временем — ровно в виде `toISOString()` (`2026-11-05T10:00:00.000Z`). У каждого момента одна запись, поэтому сроки сравниваются как строки — это нужно слиянию.
- **Авторство** (`createdBy/At`, `updatedBy/At`) проставляет `graph-core` из контекста операции; клиент его не передаёт. `updatedBy/At` меняется при правке содержимого (поля, статус, превращение блока в роадмапу), но не при перемещении (`moveNodes`, `moveTask`) и не когда задаче ставят или снимают предупреждение: это не правка самой задачи.
- **Изменение без новых значений** (то же название, на то же место) ничего не меняет и возвращает тот же граф: интерфейс ничего не перерисовывает, авторство не трогается.
- Из сообщения берутся только известные поля: лишнее (например, `type` или `number` в изменении задачи) в граф не попадает. Id вроде `constructor` или `__proto__` работают как обычные id.

### Поля задачи

- **Ответственные** — несколько (до 10), все равноправны; задача видна в личном списке у каждого. Сознательно не как в Linear/Jira/Asana (там один исполнитель ради однозначной ответственности). Хранится списком, поэтому «только один» потом — просто лимит 1.
- **Срок** — дата или дата со временем. Со временем хранится момент в UTC, и каждый видит его в своём часовом поясе (как метки времени в Discord). Без времени — календарная дата, одинаковая для всех: иначе «15 ноября» у кого-то превращалось бы в 14-е.
- **Приоритет** — фиксированная шкала: нет, низкий, средний, высокий, срочный (как в Linear; предложено).
- **Метки** — короткие цветные ярлыки (`frontend`, `баг`, `дизайн`) для фильтрации. Список меток общий на envi, как у репозитория на GitHub: один на все ветки, создание и удаление меток не идёт через PR. Задача хранит ссылки на метки; ссылка на удалённую метку просто не показывается.
- **Оценка** — число в единицах envi (`estimateUnit`).
- **Номер** — `{taskPrefix}-{число}`, как в Linear и Jira. Счётчик один на envi, номер выдаёт сервер при подтверждении создания, поэтому номера уникальны во всех ветках. Задача, созданная офлайн, получает номер при подключении. Номер не меняется и не переиспользуется — в том числе при переносе задачи в другой блок. Позже по номеру можно будет связывать коммиты с задачами.

**Сводка блока** вычисляется, а не хранится: прогресс (сколько задач выполнено), сумма оценок и сколько осталось, все ответственные его задач. Роадмапа показывает то же по всем блокам внутри.

**Просрочка** (`overdue`) вычисляется вместе с состояниями: у задачи — срок прошёл, а она не `done`; у блока, роадмапы и milestone — прошёл их собственный срок, а они не выполнены. Текущее время передаётся в вычисление параметром, чтобы функция оставалась чистой и тестируемой.

### Перенос задач

Задачу можно перетаскивать внутри блока и в другой блок (`moveTask`): номер, поля и стрелки сохраняются. Переносить можно и в блок на другом уровне. Если из-за переноса стрелка задачи образовала бы цикл, перенос отклоняется.

### Превращение блока в роадмапу

Разросшийся блок превращается в роадмапу (`blockToRoadmap`): внутри появляется блок с тем же названием, и все задачи переезжают туда с номерами, полями и стрелками. Стрелки задач остаются точными («после задачи X»), а снаружи рисуются пунктиром из роадмапы. Входы и выход самой ноды остаются как были.

Обратно в блок (`roadmapToBlock`) превращается только пустая роадмапа. Блок внутри вложенной роадмапы стать роадмапой не может — вложенность максимум 1.

### Стрелки через границу роадмапы

Стрелка может идти изнутри роадмапы наружу, снаружи внутрь и из одной роадмапы в другую. Зависимость остаётся точной: от того блока или задачи, где она начинается, к той ноде, куда ведёт.

- **Снаружи** (на корневом уровне) такая стрелка рисуется **пунктиром** из ноды-роадмапы или в неё — внутренние блоки здесь не видны.
- **Внутри** роадмапы стрелка, уходящая наружу или приходящая снаружи, показывается пунктирным «хвостиком» у края с подписью, куда или откуда она ведёт; клик переходит к той ноде.
- Тупики через границу ловит проверка циклов (см. «Инварианты»).

### Одновременное редактирование одного поля

Блокировок нет. Когда кто-то редактирует текстовое поле (название, описание), остальные видят рядом с полем его аватар «печатает» — это presence, не сохраняется. Если оба всё же сохранили, побеждает последний.

### Вычисляемые состояния (чистая функция от графа и настроек envi)

Источник стрелки выполнен, если:
- это задача — она `done` (или `in_review` при `reviewUnlocks`);
- это нода — её состояние `done`.

Состояния:
- **Задача**: `done`, если она выполнена. Иначе `locked`, если её блок `locked`. Иначе `available` (или `in_progress` / `in_review` по статусу).
- **Блок**: `locked`, если хоть одна входящая стрелка не выполнена или роадмапа, внутри которой он лежит, `locked`. Иначе `done`, когда выполнены все его задачи. **Пустой блок не выполнен** и показывается как «пусто» — иначе пустой блок сразу разблокировал бы всё после себя. Иначе `in_progress`, если хоть одна задача начата, или `available`.
- **Роадмапа**: `locked` по своим входам, как блок. `done`, когда выполнены все ноды внутри; пустая — «пусто».
- **Milestone**: `done`, когда выполнены все входящие стрелки; без входящих — «пусто», и ничего не разблокирует.

«На проверке» считается выполненным по одной настройке `reviewUnlocks` везде — и для стрелки от задачи, и для готовности блока. Иначе внутри блока работа шла бы дальше, а снаружи стояла.

Нода с пометкой «засчитано» считается выполненной для всего после неё (стрелки от неё, готовность роадмапы, в которой она лежит), даже если в ней есть невыполненное. Сама выполненность нод уже считается в `graph-core` ([doneness.ts](packages/graph-core/src/doneness.ts)); полные состояния для интерфейса строятся на том же обходе.

### Задачи не по порядку

Запрета нет: задачу в заблокированном блоке можно взять в работу и выполнить. Такая задача получает пометку «Досрочно» / «Early» (рабочее название; это строка в переводах, менять дёшево). Пометка вычисляется: она есть, пока задача начата или выполнена, а её блок `locked`.

### Предупреждение «предыдущая задача изменена»

- Когда задача выходит из выполненного состояния (переоткрыли `done`, master отклонил `in_review` при `reviewUnlocks`), предупреждение получают все задачи дальше по стрелкам — и от этой задачи, и от её блока (он тоже перестал быть выполненным) — со статусом `in_progress` / `in_review` / `done`. Статусы их не меняются.
- На задаче — кружок с `!`. Описание: «Предыдущая задача {taskName} была изменена». Действия: «Убрать предупреждение у этой задачи», «Убрать у всех последующих задач».
- Предупреждения — часть графа (одинаковы для всех) и ставятся той же операцией, что изменила статус; снимаются операцией `dismissWarnings`.

«Изменением» считается только выход из выполненного состояния: правки названия или описания предупреждений не дают, иначе их начнут закрывать не читая. Предупреждение общее: снял один — снято у всех.

**Кто именно «дальше по стрелкам»** — те задачи, которые эта задача заблокирует, перестав быть выполненной:
- задачи нод, куда ведут стрелки от самой задачи;
- если её блок был выполнен, он перестаёт быть выполненным — значит, и задачи нод по стрелкам от блока; если блок внутри роадмапы — то и по стрелкам от роадмапы;
- заблокированная нода тоже перестаёт быть выполненной, и всё идёт дальше по её стрелкам; у заблокированной роадмапы — всё внутри.

Не получают предупреждение соседние задачи того же блока и то, что ждёт только другие задачи заблокированного блока: те задачи остались выполненными. Если блок «засчитан», переоткрытие его задачи не блокирует то, что после блока.

Если ту же задачу переоткрыли снова, а предупреждение от неё ещё висит, второе не добавляется — у первого обновляется время.

Источник предупреждения (`source`) — переоткрытая задача или нода, которая перестала быть выполненной (см. ниже). Текст в интерфейсе — по источнику: «Предыдущая задача {задача} снова не выполнена» или «{нода} снова не выполнена».

**«Убрать у всех последующих»** снимает предупреждения у этой задачи и у задач после неё, но только от тех же источников, что у этой задачи. Предупреждения от других источников дальше по цепочке остаются: их ещё никто не видел.

### Когда выполненное снова не выполнено

Выполненная нода может перестать быть выполненной не только от переоткрытой задачи:
- в выполненный блок добавили невыполненную задачу или перенесли её туда;
- в выполненную ноду провели стрелку от ещё не выполненного;
- в выполненную роадмапу добавили ноду;
- из выполненного блока удалили последнюю задачу (блок стал «пусто»);
- с ноды сняли «засчитано» (см. ниже).

Правило одно: всё, что после такой ноды, снова блокируется, а начатые и выполненные задачи там получают предупреждение с этой нодой как источником. Если по цепочке перестали быть выполненными несколько нод (блок → роадмапа, в которой он лежит), источник — первая. Задачи самой ноды предупреждение не получают: изменение сделали в ней самой.

**Перед таким изменением интерфейс спрашивает** (функция `previewRelock` говорит, что заблокируется, и ничего не меняет): «Последующие задачи (N) снова заблокируются».
- **Блокировать** — изменение как есть, предупреждения дальше.
- **Не блокировать** — изменение уходит с флагом `keepDone`: нода получает пометку **«засчитано»** (кто и когда) и для всего после неё остаётся выполненной; предупреждений нет. Пометку получает только первая в цепочке нода — остальное после неё и так остаётся выполненным.
- **Отмена** — ничего не меняется.

Пометка «засчитано» видна на ноде. Она снимается сама, когда нода снова выполнена по-настоящему, — тогда следующее такое изменение снова спросит. Снять её можно и вручную (`updateNode` с `countedDone: null`): это как «блокировать» — последующее блокируется, начатое получает предупреждение. Поставить пометку правкой нельзя, только выбором «не блокировать».

Переоткрытие задачи без диалога (решено 2026-11-05): переоткрыли — значит, работа не сделана; к тому же стрелки от самой задачи «засчитать» нельзя — пометка ставится на ноду, а не на задачу.

### Инварианты (проверяет `graph-core` на каждой операции)

1. Нет циклов и тупиков. Проверка идёт по всему графу сразу, с учётом вложенности: роадмапа R раскладывается на «начало R» (в него входят её входящие стрелки, из него — путь ко всем нодам внутри) и «конец R» (в него — от всех нод внутри, из него — её исходящие стрелки). Стрелка от задачи считается стрелкой от её блока. Так ловится и тупик вроде «блок внутри R ждёт ноду X, а X ждёт всю R».
2. Координаты нод — целые числа.
3. Источник и цель стрелки существуют; нет петель (в том числе от задачи к её же блоку) и дубликатов.
4. Роадмапа может стоять только на корневом уровне (вложенность максимум 1); `parentId` указывает только на роадмапу.
5. Задачи лежат только в блоках.
6. Удаление ноды удаляет её задачи и все связанные стрелки, у роадмапы — и всё внутри; удаление задачи — её стрелки. Всё в той же операции.
7. `in_review` — только при `statusMode = 'review'`; подтвердить `in_review` → `done` может только master.

## Операции

Точные типы — `Op` в [types.ts](packages/graph-core/src/types.ts), коды ошибок — в [errors.ts](packages/graph-core/src/errors.ts).

| Операция | Что делает |
|---|---|
| `createNode` / `updateNode` / `deleteNode` | Ноды. Поле, которого нет у этого типа ноды, — ошибка `FIELD_NOT_APPLICABLE`. Удаление забирает задачи и стрелки, а у роадмапы — всё внутри. |
| `moveNodes` | Двигает ноды: и перетаскивание, и автораскладка. Одна нода дважды в одной операции — ошибка. |
| `blockToRoadmap` / `roadmapToBlock` | Превращение блока в роадмапу и обратно (см. выше). |
| `createTask` / `updateTask` / `deleteTask` | Задачи. Номер выдаёт сервер, авторство проставляет graph-core — клиент их не передаёт. |
| `moveTask` | Порядок задачи в блоке и перенос в другой блок. |
| `createEdge` / `deleteEdge` | Стрелки «блокирует». |
| `dismissWarnings` | Снимает предупреждения у задачи или у неё и всех следующих. |
| `restore` | Возвращает удалённые ноды, задачи и стрелки как были — с теми же id и номерами (undo удаления, корзина). Сервер принимает только то, что совпадает с его копией в корзине, чтобы клиент не мог подсунуть поддельные данные. |

Операция применяется функцией `applyOp(graph, op, ctx)` из `graph-core` ([apply.ts](packages/graph-core/src/apply.ts)), которая возвращает новый граф или ошибку. Она получает контекст `{ actor, settings, now }`: кто действует (с итоговой ролью), настройки envi, влияющие на правила графа (`statusMode`, `reviewUnlocks`), и текущее время. Остальные настройки envi graph-core не нужны и живут на сервере. Обёртка операции для протокола (`opId`, `branchId`, `baseVersion`) появится на шаге 4.

У любой операции есть необязательный флаг `keepDone` — выбор «не блокировать» (см. «Когда выполненное снова не выполнено»). Функция `previewRelock(graph, op, ctx)` проверяет операцию так же, как `applyOp`, и говорит, какие ноды перестанут быть выполненными и какие задачи заблокируются, ничего не меняя: по ней интерфейс решает, спрашивать ли.

Ошибки — коды с данными для сообщения (например, `CYCLE` с путём цикла для подсветки). Список всех кодов `GRAPH_ERROR_CODES` нужен интерфейсу, чтобы проверить, что у каждого кода есть перевод.

В режиме `review` кнопка «выполнено» у member отправляет статус `in_review`. Если member пришлёт `done`, операция отклоняется (`FORBIDDEN`).

Позиции вынесены в отдельную операцию: при перетаскивании операция уходит на отпускание мыши, а промежуточное движение видно другим через presence (не сохраняется).

## Реалтайм внутри одной ветки

1. Клиент подключается по WebSocket и подписывается на `(envi, ветка)`. Сервер присылает снимок и номер версии.
2. Клиент применяет операцию у себя сразу (оптимистично) и отправляет её.
3. На сервере для каждой открытой ветки есть «комната» в памяти. Операции применяются строго по очереди: проверка прав, валидация через `graph-core`, затем в одной транзакции Postgres запись в лог операций и обновление таблиц `nodes`, `tasks` и `edges`, затем `version + 1` и рассылка всем.
4. Если операция нарушает инвариант или права, сервер отклоняет её с причиной; клиент откатывает.
5. Когда приходит чужая операция, клиент применяет её к подтверждённому состоянию и заново накладывает свои неподтверждённые операции поверх.
6. Курсоры и выделение идут через тот же WebSocket как presence: не сохраняются, отправляются не чаще ~20 раз в секунду.

Ограничение: один серверный процесс. Масштабирование позже — маршрутизация envi на конкретный процесс.

Лог операций в БД бесплатно даёт аудит-лог («кто и когда что поменял») и основу для undo.

## Ветки, PR и слияние

- **Ветка** создаётся копией графа исходной ветки; запоминаются исходная ветка и её версия в момент ответвления (снимок-база).
- Внутри ветки — тот же реалтайм, можно работать вдвоём.
- **Слияние — трёхстороннее по записям**, как в git, только по нодам и полям, а не по строкам текста: `merge(база, наша ветка, целевая ветка) → { результат, конфликты }`. Это чистая функция в `graph-core`.
- **Конфликты** (только смысловые изменения):
  - одно и то же поле одной ноды изменено с обеих сторон по-разному — выбрать значение;
  - нода или задача изменена с одной стороны и удалена с другой — оставить или удалить;
  - новое ребро ведёт к ноде, удалённой в целевой ветке;
  - после слияния появился цикл — показать цикл и выбрать, какое ребро не переносить.
- **Позиции не конфликтуют никогда.** Если ноду двигали с обеих сторон: при равных правах берётся последнее перемещение; если у автора PR права ниже, чем у того, кто двигал в целевой ветке, молча остаются целевые позиции, а в preview пишется «позиции N нод не перенесены». Новые ноды приходят с позициями из ветки.
- **Списки (ответственные, метки) сливаются как множества**: добавления и удаления с обеих сторон объединяются, конфликтов нет.
- **Preview** — результат слияния на холсте: добавленное зелёным, удалённое красным полупрозрачным, изменённое жёлтым, конфликты с выбором решения.
- **Мерж** выполняет сервер: пересчитывает слияние на текущей версии целевой ветки (если она ушла вперёд с момента preview, preview обновляется), применяет результат операциями в одной транзакции. Подключённые клиенты получают изменения обычным реалтаймом.

## Офлайн

- Клиент хранит в IndexedDB последний снимок ветки и свои неподтверждённые операции.
- Без сети: плашка «нет сети — изменения локальные», работа продолжается в локальной ветке от последней известной версии.
- После подключения: трёхстороннее слияние локальной ветки с текущей версией. Дальше по `offlineMerge`: `auto` — без конфликтов применяется само, с конфликтами автору показывается preview; `always-pr` — открывается PR.
- Короткий обрыв на пару секунд проходит по тому же пути: без конфликтов он для пользователя незаметен.

## Undo

В MVP, по образцу Figma:
- Отменяются только **свои** действия. Отмена — новая обратная операция, она проходит те же проверки и права, что и обычная.
- Одно действие пользователя — один шаг отмены: перетаскивание пяти нод, автораскладка, каскадное удаление блока откатываются целиком.
- Если после вас то же поле поменял кто-то другой, отмена этого поля **пропускается**, и появляется подсказка «не отменено: поле уже изменил {имя}». Чужая работа не затирается.
- История отмен живёт **только в текущей сессии** и отдельно для каждой ветки: после перезагрузки страницы она пуста. Старое возвращается через историю изменений задачи и корзину.
- Обратную операцию для любой операции строит `graph-core` (чистая функция). Свойство для тестов: применить операцию, затем обратную — граф совпадает с исходным.
- Отмена должна возвращать и последствия: предупреждения, которые операция поставила, и пометку «засчитано», которую она поставила или сняла. Как именно — решим в подшаге с обратными операциями.

## Организации и доступ

- Схема как у Linear и Vercel: envi **всегда** принадлежит организации (одно поле `workspace_id`), поэтому проверка прав идёт одним путём. Схему GitHub (владелец — пользователь или организация) отвергли: два пути проверки прав — больше мест для дыр, плюс отдельная логика переноса.
- При регистрации молча создаётся личная организация «Личное». Пользователь может состоять в нескольких организациях и переключаться между ними.
- Перенос envi в другую организацию — смена владельца, одна операция.
- Соло — это envi с одним участником, отдельного режима нет.
- Роли на envi: master, member, viewer (см. «Роли»).
- Роли организации: **владелец** (их может быть несколько; управляет организацией, автоматически master во всех её envi) и **участник** (видит envi по их настройке `visibility`). Роль **админа** (управляет людьми и envi, но не удаляет организацию и не трогает оплату) добавим вместе с оплатой: роль хранится значением, поэтому это не потребует переделки данных.

### Приглашения

- **Ссылка-приглашение** — master создаёт ссылку с ролью и сроком действия, может отозвать.
- **По почте** — в базовом виде: письмо со ссылкой-приглашением.
- **По нику** — у пользователей уникальные ники. Предложено: латиница, цифры, `_` и `-`, длина 3–32, без учёта регистра; ник можно менять, как на GitHub.

## Корзина

Удалённая нода или задача (вместе со всем содержимым и стрелками) хранится на сервере 30 дней (предложено), её можно восстановить операцией `restore` — с теми же id и номерами. Восстановление проходит те же проверки, что и создание (свободные id, родитель, блок задачи, значения полей), кроме прав на статусы: это возврат прежнего состояния, а не новая правка, иначе member в режиме `review` не смог бы отменить удаление блока с выполненными задачами. Стрелки, которые встать обратно не могут, пропускаются, остальное восстанавливается: конца стрелки уже нет, такая же стрелка уже есть или стрелка замкнула бы цикл с тем, что добавили после удаления. Восстанавливать может тот, кто удалил, и master. При защищённом `main` восстановление — обычное изменение структуры: member делает его через ветку и PR, master — сразу.

## Аккаунты и вход

- Три способа: GitHub, Google, своя регистрация (почта + пароль).
- В кабинете после регистрации можно по желанию привязать к аккаунту другие способы входа (почту, GitHub, Google). Ничего не навязываем при регистрации.
- **Аккаунты никогда не склеиваются автоматически** по совпадению почты — привязка только из кабинета, когда пользователь уже вошёл. Автосклейка — классический способ захватить чужой аккаунт.
- Реализация: сессии свои (httpOnly cookie, сессии в Postgres); OAuth через библиотеку Arctic (протокол руками не пишем); пароли — хеш argon2id.
- Своя регистрация требует писем (подтверждение почты, сброс пароля). Сами пишем шаблоны, токены и `sendEmail()`; доставку отдаём сервису (Resend, Postmark, Amazon SES или подобный) — свой почтовый сервер не доставит письма мимо спама. Понадобится свой домен. В разработке — Mailpit в Docker: ловит все письма локально и показывает в браузере.
- GitHub для входа и GitHub для интеграции «коммит → статус» требуют разных прав доступа; при входе просим только профиль и почту.

**Открыто:** какой почтовый сервис — выберем при деплое (см. «Хостинг»).

## Безопасность

- **SQL-инъекции:** все запросы через Drizzle с параметрами. Аварийные выходы (`sql.raw` и строковая склейка в запросах) запрещены правилом линтера и на ревью.
- **Права на каждой операции:** сервер проверяет, что пользователь — участник envi и его роль разрешает действие. Id из запроса никогда не считается доказательством доступа.
- **XSS:** React экранирует текст сам; `dangerouslySetInnerHTML` не используем. Если описания будут рендериться как Markdown, HTML проходит через санитайзер.
- **Валидация входа:** каждое сообщение WebSocket и тело HTTP-запроса проверяется по схеме до того, как попадёт в логику.

## Не входит в MVP

Ноды Gate и Decision, табличный вид, интеграции (GitHub, Slack), SSO для организаций, импорт из Jira и Linear, слой рисования, комментарии к блокам, вход у отдельной задачи (формат заложен).

## Импорт списка через ИИ

У человека есть список дел, и он хочет сразу получить из него роадмапу. Своего ИИ у нас нет и платить за него мы не хотим: ИИ работает на стороне пользователя (ChatGPT, Claude — что у него есть). Если позже появится свой ИИ, он возьмёт ту же инструкцию и тот же формат.

1. В приложении кнопка «Импорт из списка». Пользователь вставляет свой список, а мы собираем готовую инструкцию: правила формата, пример и его список. Кнопка «Скопировать».
2. Пользователь отдаёт инструкцию своему ИИ и вставляет ответ обратно.
3. Мы достаём из ответа JSON (ИИ часто оборачивает его в ```` ``` ```` и добавляет текст вокруг) и проверяем его по схеме, а затем теми же правилами `graph-core` — циклы и мусор не пройдут. Ошибки показываем понятно: что не так и где.
4. Блоки раскладываются автоматически, показывается preview, пользователь подтверждает.

**Куда** — пользователь выбирает сам:
- **новый envi** из этого списка;
- **существующий envi** — список добавляется отдельными блоками на свободное место рядом с графом, дальше пользователь сам расставляет их как нужно. Если `main` защищён, добавление идёт через ветку и PR, как любое изменение структуры.

**ИИ возвращает данные, а не код.** Вставленный код мы бы выполняли с правами пользователя — пользователю могли бы подсунуть «код», который украдёт сессию или удалит данные. Данные же только разбираются и проверяются, ничего не выполняется.

**Формат** — максимально простой для ИИ: без id и координат (их создаём мы), ссылки по коротким ключам, версия формата для совместимости:

```json
{
  "format": "cooptracker-import", "version": 1,
  "blocks": [
    { "key": "auth", "title": "Авторизация",
      "tasks": [ { "key": "login", "title": "Логин", "priority": "high" } ] },
    { "key": "profile", "title": "Профиль", "tasks": [] }
  ],
  "arrows": [ { "from": "auth.login", "to": "profile" } ]
}
```

Это надстройка над импортом JSON: тот же путь проверки и создания, плюс инструкция для ИИ, извлечение данных из ответа и preview.

## Ещё в MVP

- **Уведомления в приложении** (колокольчик): вас назначили, задача ждёт вашей проверки, новый PR, появилось предупреждение. Хранятся на сервере, приходят по WebSocket. Письма — позже.
- **Экспорт и импорт envi в JSON**: резервная копия и перенос. В файле — версия формата, чтобы старые файлы читались после изменений схемы. Импорт создаёт новый envi с новыми id.
- **Телефон**: просмотр графа и смена статуса задачи. Полное редактирование графа — только на компьютере.
- **История изменений задачи** в инспекторе: кто, когда и что поменял. Берётся из лога операций.

## Хостинг и почта

Решим при деплое — для разработки они не нужны (Postgres и Mailpit в Docker). Рынок пока не определён; разработчики в Кыргызстане и Чехии, поэтому выбор зависит от того, кто и чем сможет платить. Код не привязываем к провайдеру: всё запускается через `docker compose`, письма — через свою `sendEmail()`.

Ограничение на выбор: сервер держит долгие WebSocket-соединения и комнаты в памяти, поэтому нужен обычный сервер или контейнер (VPS или PaaS), а не serverless-функции.

Если будут пользователи из ЕС (друг в Чехии — уже ЕС), действует GDPR: политика конфиденциальности, удаление аккаунта, выгрузка своих данных. Выгрузка частично покрывается экспортом в JSON; удаление аккаунта заложим на шаге авторизации.

## Порядок работы

Каждый шаг — отдельная сессия и коммит, с тестами до перехода к следующему.

1. `graph-core`: типы, операции, применение и валидация, обратные операции (для undo), вычисляемые состояния (включая «Досрочно», просрочку, предупреждения), инварианты. Юнит-тесты и property-based тесты (случайные графы и последовательности операций; инварианты держатся всегда; операция + обратная = исходный граф).
2. `graph-core`: трёхстороннее слияние и конфликты. Самая сложная логика — поэтому рано и чистой функцией.
3. `server`: Fastify, Postgres в `docker compose`, схема и миграции на Drizzle, авторизация (три способа, привязка в кабинете, Mailpit, удаление аккаунта), организации, envi и настройки, роли, приглашения, метки, нумерация задач.
4. `server`: комнаты и протокол WebSocket — снимок, операции, проверка прав, отклонение, presence (курсоры, «печатает»), уведомления. Интеграционные тесты с двумя клиентами.
5. `web`: холст на React Flow, ноды в стиле референса, инспектор, редактирование, синхронизация, курсоры, автораскладка, переводы, undo. **После этого шага уже можно работать вдвоём.**
6. `web`: вложенные роадмапы (вход в роадмапу, навигационная цепочка, пунктирные стрелки через границу), история изменений задачи, колокольчик уведомлений, вид для телефона, режим фокуса, командная палитра Ctrl+K, фильтры, направляющие.
7. Ветки, PR, preview с diff и разрешение конфликтов; режим `review` для статусов.
8. Офлайн: IndexedDB, плашка, слияние при подключении.
9. Корзина, экспорт и импорт JSON, импорт списка через ИИ.
